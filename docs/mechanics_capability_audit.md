## Source-to-decision path (before this hardening pass)

Original `.echoreplay` line / bridge HTTP response → `adapter.EchoVRSession` → shared `Mapper.MapSessionAt` → normalized `PlayerTelemetryFrame` → `FrameValidator` → `FeatureExtractor` / reconstructed `ThrowEvent` → detector → event validation / source-quality and shadow gates → causal deduplication / rate limit → scorer → stored events, coverage and cases. Offline reprocessing can rerun the mapper from retained raw JSON; normalized-only legacy records cannot recover missing source fields. Live processing on a server does not make its client feed authoritative.

| Required input | Actual source and time basis | Present / validity handling at audit | Authority / limitation |
| --- | --- | --- | --- |
| Disc position, velocity | `/session.disc`; replay line sample time or bridge receive time, relative monotonic timestamp | Finite/bounds validation; invalid disc removed; velocity is not derived from disc position | Client-reported sampled game state, not authoritative acquisition/release tick |
| Player movement | `players[].velocity` and separate arena pose deltas | Normalized optional vector exists, but raw JSON's array defaults previously turned omitted velocity into observed zero; pose velocity is a different derived quantity | Sampled game-reported movement / inferred pose motion; exact release alignment not established |
| Head/body/hands | head/body `position`; hands `pos` | Head optional; zero/nonfinite hand positions treated as tracking loss; far-hand sanity filter | Sampled arena transforms; local playspace root is not interchangeable |

| Attachment / grabbing hand | `holding_left`, `holding_right`; top-level/player possession also present | Exact strings/hand identity lost; global `PossessionKnown` exists for STATE_008, but legacy release reconstruction still consumes a fallback boolean | Explicit hand observations can support sampled state; sticky possession alone cannot identify acquisition/release |

## Confirmed defects / implementation priorities

1. Preserve known attachment state and hand candidates; suppress unknown/ambiguous releases and hand transfers, rather than converting missing input to free.
2. Preserve invalid orientation through derivatives; normalize valid near-unit quaternions; include full orientation bases in snapshot identity.
3. Bind local throw diagnostics to their actual client, source continuity and event interval. Value changes alone do not prove event freshness.
4. Replace STATE_001's enlarged-radius/current-held heuristic with a disc-only, versioned-rule assessment. Keep measurement uncertainty separate. No interpolation across attachment snaps.
5. Record the 0.25 m and 19/4.7 rules explicitly, without claiming engine validation or changing the separate configured 18.9 m/s cap.
6. Use precise assessment kinds and consistent/inconclusive/anomaly/validated_violation outcomes. Precision alone, a normal nonzero setting, and community cheat names are not violation evidence.
7. Preserve bounded, reproducible per-event assessments and source/validity context; protect all unvalidated conclusions from scoring/enforcement.

## External verification boundary

The [EchoTools HTTP schema](https://github.com/EchoTools/nevr-proto/blob/2450c39d820bf496913e6150ef2e368266987905/engine/v1/engine_http.proto) separately defines hand `pos`, body `position`, holding fields, player velocity, last-score speed and top-level last-throw components. Its field list does not prove a capture is authoritative or establish the 0.25 m distance convention, 19/4.7 rule, permitted wrist-setting range or complete release solver.

The [runtime snapshot reader](https://github.com/EchoTools/nevr-runtime/blob/a692a304a79a75564f6b660ea81a96137b433357/src/runtime/server/telemetry_streamer.cpp) copies sampled game memory. Its symbol inventory names grab and throw operations, but names are not numeric limits or validated mechanics. Exact rule/build validity remains unresolved. Current recordings cannot prove millisecond-scale remote input automation.

## Implemented measurement contracts

- Hand `holding_left` / `holding_right` strings survive normalization. Explicit global attachment is `free`, `held` with persistent player and plausible hands, or `unknown`; missing/conflicting samples are not free. A release is published only after a second consecutive known-free observation. Its evidence remains anchored to the original last-held→first-free interval, not the later confirmation or later player motion. Same-player hand transfers/brief reattachments cancel; EOF and missing-motion cases retain an inconclusive record, never an invented throw.
- Observation context records the actual sample-time basis, session, recorder source and local identity. It does **not** invent capture timestamps, attested build, remote controls or collision authority. Local changed-value `last_throw` details are retained only when uniquely bound to the recording client and the same source/sample. They no longer override sampled speed or create confidence 1. Identical-valued successive local throws cannot be distinguished from stale polling without a producer event ID.
- Explicit observed-orientation flags distinguish genuine identity from missing/fallback data. Valid near-unit quaternions normalize before sign-invariant angular distance; all basis axes participate in live sample identity. Wrist rates retain validity, and unknown rates cannot become low-variance zero signatures. Physical hand-motion/disc-angle evidence is not a WristAngleOffset reading.
- Raw vector presence survives JSON round-trips and live duplicate checks. Omitted/null/incomplete player velocity stays unavailable; explicit `[0,0,0]` remains observed zero. Missing either disc position or velocity drops the normalized disc observation. Since attachment context currently belongs to that observation, such samples also abstain from attachment-only acquisition diagnostics rather than inventing a partial event. Typed Go fixture producers explicitly provide their arrays; decoded external JSON never receives that assumption.
- Boost presence is explicit. The HTTP mapper supplies unknown, not false. MOV_004/005 and extracted activation histories require known consecutive source-consistent inputs and an observed pre-boost baseline; an already-active initial sample is not a new activation. Unknown boost cannot label a movement interval as known nonboosting.
- `project_rules` contains `owner-2026-09-08-v1`, exactly 0.25 m, 19 m/s and 4.7 m/s. The legacy unused `physics.grab_range` is not a legality threshold. STATE_001 no longer uses its former 3 m held-pose comparison, body fallback or movement credit. Current raw hand-origin/disc-center distances are descriptive only because the owner's distance convention is not verified.
- Pure rule evaluators require private audited knowledge of the rule/build, source and bounds. No config or telemetry flag can enable that knowledge in this implementation. Synthetic tests construct hypothetical knowledge inside the package to exercise exact inclusive boundaries and controlled contradictions; no production source currently qualifies. A record proven against such knowledge retains its verification reference and geometry where applicable.
- THROW_005 includes observed misses/non-goal releases in bounded supporting statistics and never emits a scored accuracy finding. It does not invent pocket geometry, compare gaze/hand-forward to a target, or declare bank shots impossible. THROW_006 is separate free-flight review, not mags: unknown attachment, contacts, gaps, source changes and incomplete tracks remain inconclusive. STATE_008 is named Pre-catch Trajectory Review; its existing trajectory observations remain zero-weight shadow signals with unverified cause and actor.
- New diagnostics use four precise kinds and `consistent`, `inconclusive`, `anomaly`, `validated_violation` outcomes. Each player/check retains at most 128 evidence records with separate omitted/invalid counts and at most 128 raw samples per record. THROW_005 retains every release in its 50-release supporting window, including exact scalar speeds and explicitly inferred reference targets; THROW_006 retains every inspected flight sample, including pre-distance-gate baselines, for up to 120 intervals. Release-based checks share the same source-bound event identity. They are stored independently of scores; live chunk merge does not claim complete coverage. Duplicated/stale player samples cannot rewind derivatives or dispatch detectors again.
- In the desktop assessment, select a detector and **Explain checks** to inspect **Mechanics assessments**. Zero-signal/inconclusive records remain accessible. Evidence includes intervals, rules, raw samples, limitations and exact-frame Spark/physics actions. Blinded review hides it. Re-import originals rather than treating absent legacy validity fields as observed.

The [unofficial API documentation](https://github.com/Ajedi32/echovr_api_docs#last_throw) identifies the top-level throw details with the local client, and separately describes [goal-entry disc speed](https://github.com/Ajedi32/echovr_api_docs#last_scoredisc_speed). Its current player-possession description is generic; the brief's more specific sticky-possession wording was not independently established there. The implementation relies on explicit hand attachment regardless.

Nakama's [logged settings structure](https://github.com/EchoTools/nakama/blob/6e9e5dbb81f116bdd56cffdd81b17aa4aa453867/server/evr/login_remotelogset_messages.go) and [round-trip fixture](https://github.com/EchoTools/nakama/blob/6e9e5dbb81f116bdd56cffdd81b17aa4aa453867/server/evr/login_remotelogset_test.go) confirm a `wristangleoffset` field and a nonzero example. They do not establish a permitted range, apply that setting to remote replay players, or supply this anticheat with event-aligned settings. Settings-integrity assessments therefore remain inconclusive.

## Changed areas and remaining validation gates

Changes are concentrated in `internal/adapter` / `cmd/bridge` (source mapping and freshness), `internal/model` (validity and bounded evidence), `internal/pipeline` (attachment/release reconstruction and diagnostics), `internal/mechanics` (private-knowledge pure rule checks), the affected movement/bio/state/throw detectors, config/promotion guards, SQLite coverage persistence, and desktop evidence rendering. Corresponding unit/integration fixtures were made explicit rather than weakening missing-input guards. The only recording changed in source control is the generated, fictional `tests/fixtures/synthetic_session.echoreplay`, which now states the hand attachments its test scenario intends; no original replay is included.

No Echo engine/build rule was independently validated by this pass. The exact grab-distance definition, authoritative acquisition/release times and error bounds, permitted setting range, remote input provenance, obstacle/collision model, and verified release-velocity solver are still missing. Establish those against a pinned build and independently reviewed positive/negative recordings before enabling any enforcement capability. Unknown data must remain an abstention; it is neither a clean-player certificate nor permission to enlarge a legal limit.
